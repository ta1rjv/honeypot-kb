ADR 0011: Opt-in webhook alert notifications, SMTP deferred

kaynak: docs/decisions/0011-webhook-alert-notifications.md

Status: accepted (2026-10-11). Implementation: IMPLEMENTED in 0.4.0; VALIDATED on [gizlendi] (2026-10-11), including delivery over the real network path in the final re-run with a tarball from cd7a0e1 (TESTING.md); production use with an operator receiver NOT VERIFIED.

Context: operators want to learn about severe alerts without keeping the dashboard open. Containment (ADR 0003) makes this hard: the output chain drops every new connection except DNS, _apt HTTP(S) and optional NTP/DHCP, and the backend uid hpintel has no egress at all. Any notification therefore needs a new egress path, and that path must never become usable by the honeypot uid cowrie, by an attacker who controls alert text, or as a general-purpose exit for a compromised backend. Candidate channels were an HTTP(S) webhook and mail over SMTP.

Decision:

  1. Implement one channel, an HTTP(S) webhook (backend/hpintel/notify.py), disabled by default. Enabling it takes two separate operator actions: HP_WEBHOOK_DEST4/HP_WEBHOOK_PORT in the setup.sh configuration (the firewall) and HPINTEL_WEBHOOK_URL in hpintel.env (the backend).
  2. Firewall: the renderer emits one rule for meta skuid "hpintel", one IPv4 address literal and one TCP port, placed after the uid cowrie drop and directly before the final egress_blocked drop (NETWORK.md). No CIDR, no host name, no IPv6; unspecified, 0.0.0.0/8, 198.18.0.0/15, loopback, multicast, broadcast, link-local and reserved addresses are rejected; private and 100.64.0.0/10 addresses are allowed for an operator-side receiver. Without the keys the ruleset is byte-identical to 0.3.1.
  3. Transport: Python standard library only; environment proxies ignored, redirects refused, TLS certificate and host name verification always on (optional private CA file, https only), 5 s per operation and 10 s per delivery. The URL has no userinfo or fragment; only scheme://host:port is ever logged or returned by the API; error reasons are built from type names, status codes and errno values only.
  4. Content: one compact JSON document per alert with the alert fields only (id, timestamp, severity, kind, session id, source IP, message), each clipped to 512 characters. With HPINTEL_WEBHOOK_SECRET the request carries X-Hpintel-Timestamp and an HMAC-SHA256 X-Hpintel-Signature over <timestamp>.<body>.
  5. Volume and backlog: minimum severity high by default, rate limit 30 per minute by default, 3 attempts with 1 minute and 5 minutes backoff. A persisted per-channel high-water mark (alert_delivery_cursors) starts at the highest existing alert id on first enable, so the backlog is never sent; after a restart, alerts older than the start time minus 15 minutes are never sent. Delivery is at least once; receivers deduplicate on alert.id.
  6. SMTP is deferred: it needs a relay, credentials stored on the host, a second egress rule (submission port to a relay) and a mail library with a larger attack surface, for no gain over a webhook that can feed a mail or chat gateway on the operator side. (Superseded by ADR 0015: Telegram and SMTP receivers were added in 0.5.0.)

Consequences:

  • Containment changes only when the operator opts in, and then by exactly one address and port for uid hpintel; uid cowrie stays fully blocked (THREAT_MODEL.md T13).
  • A compromised backend can send data to the configured receiver (accepted residual risk; the receiver is under operator control).
  • The receiver must be reachable at a fixed IPv4 address; DNS answers are not pinned, a different answer is dropped by nftables and the delivery fails.
  • On a new host setup.sh must run once without the keys (the rule needs the hpintel user), and every key change re-runs the guarded firewall step.
  • A retry still pending when hpintel restarts more than 15 minutes later is dropped (TODO.md).
  • Mail notifications remain open in TODO.md.

Alternatives considered: SMTP (deferred, see above); a wider egress rule (a CIDR, a host name resolved by nft at load time, or any destination on port 443) was rejected because it would widen the exit for a compromised backend; an outbound proxy was rejected as an extra service to harden; polling by the receiver through the dashboard API was not chosen because it needs inbound access to the dashboard, which is loopback-only by default.

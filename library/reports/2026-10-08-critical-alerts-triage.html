Summary #

The dashboard counter "open critical alerts" showed 13. That counter sums unacknowledged alerts of severity critical AND high (backend/hpintel/api.py, critical_alerts_open). All 13 are severity high; none are true critical. By kind: 8 new_payload, 5 classification:malware_deployment, across 6 distinct source IPs.

Triage result:

Group Alerts Source IP(s) Nature Verdict
B #4, #5, #6, #7, #10, #11 195.178.110.232, 92.118.39.50 Go SSH loader capability probe REAL, contained, no real malware delivered
C #8, #9 130.12.180.51 SSH propagation worm (key + config drop) REAL, highest intelligence value, spread blocked
D #12, #13 203.57.28.116, 123.139.242.2 SFTP upload named sshd REAL, binary NOT captured (collection gap)

Group B - Go SSH loader capability probe (REAL, contained): #4, #5, #6, #7, #10, #11 #

Sources: - 195.178.110.232, AS48090 DMZHOST / TECHOFF SRV LIMITED, geo BG, rDNS NXDOMAIN. 42 sessions, 3 successful logins, 2026-10-07 23:07Z..23:59Z. - 92.118.39.50, AS47890 UNMANAGED-DEDICATED-SERVERS / UNMANAGED LTD, geo RO, rDNS none. 11 sessions, 2 successful logins, 2026-10-08 12:37Z..13:21Z.

Both present client SSH-2.0-Go and run the identical command sequence after login (root with 123456 / password / 12345678):

export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:$PATH
uname=$(uname -s -v -n -m 2>/dev/null || /bin/uname ... || busybox uname ... )
printf "#!/bin/bash\necho \"xxxxxx\"\n" > filter && chmod +x filter && ./filter && rm -rf filter

This is a loader pre-flight check, not malware: a uname capability probe plus a write/chmod/execute/cleanup test that expects the output xxxxxx. The classification:malware_deployment alert fires on the chmod +x filter step (backend/hpintel/store.py, "file made executable"), but the executed file is a trivial echo. No second-stage binary was downloaded; the loader did not proceed (likely because the emulated response did not satisfy its check). Alert #4 is the filter script itself recorded as new_payload (af77b643..., #!/bin/bash\necho "xxxxxx").

Both hosters are known abuse-prone bulletproof providers. Risk scoring: each active session risk=48. Real automated threat, but low actual impact and heavily duplicated (one probe x5).

Note for the detection layer: malware_deployment at severity high overfires on a trivial chmod +x capability probe. See TODO.md.

Group C - SSH propagation worm (REAL, highest value): #8, #9 #

Source 130.12.180.51, AS202412 OMEGATECH-AS / Omegatech LTD (registry ARIN, geo US; prefix 130.12.180.0/24 allocated 2025-10-08, i.e. brand new), rDNS NXDOMAIN, client SSH-2.0-Go. One session (04bcf4604e47), login admin/admin, risk=45, categories include defense_evasion, downloader, malware_deployment, reconnaissance. Two files dropped:

Alert sha256 (short) Path Content
#8 00b6f15c2274 /tmp/sshcfg StrictHostKeyChecking no + UserKnownHostsFile /dev/null
#9 43728fbfb98b /tmp/key.ppk OpenSSH ed25519 PRIVATE key

Dropped SSH private key fingerprint (IoC; the raw key is intentionally NOT stored in this repository):

SHA256:O/at8341SoPpKvTPvMsJSgjQm30md9VTS2it25sY0vg dlr@sftp (ED25519)

This is the classic SSH worm pattern (dota / outlaw family): the bot drops its own private key plus an SSH client config that disables host-key verification, so a compromised host can log on to further targets non-interactively and spread. This is the most valuable item of the 13: it exposes the worm's propagation key and config as reusable IoCs.

Positive control result: egress is default-deny (ADR 0003), so even though the files were staged, the worm could not actually reach any third party from the honeypot. Containment worked.

Group D - SFTP upload named sshd (REAL, collection gap): #12, #13 #

Sources (both client SSH-2.0-Go, many credential attempts then one login): - 203.57.28.116, AS58519 CHINATELECOM-Ctcloud, geo CN. Session b4941bcc3ed4, root/admin, 2026-10-08 15:03Z. - 123.139.242.2, AS4837 CHINA169 / CHINA UNICOM, geo CN. Session e41c17aeeb16, root/admin, 2026-10-08 15:10Z.

Alert sha256 (short) Filename Captured?
#12 d11d2e36d17d sshd NO (available=0, size unknown)
#13 326eea0221b6 sshd NO (available=0, size unknown)

A file named sshd uploaded via SFTP is consistent with a trojanized / backdoor binary masquerading as the ssh daemon (persistence). The content was not retained, so the binary cannot be analysed. This is a known collection gap for SFTP uploads; recorded in TODO.md.

Architecture decisions

ADR 0013: Alert suppression rules (demote or suppress, alerts are never deleted)

source: docs/decisions/0013-alert-suppression-rules.md

Status: accepted (2026-10-15). Implementation: IMPLEMENTED in 0.5.0 (unreleased); covered by automated tests; NOT VALIDATED on a VM or production yet.

Context: known harmless probes (for example the Group B loader capability probe, command hash d882d096...) raise one medium alert per source IP per day and bury real alerts. Detection and classification are correct and must keep running; only the alert noise is wrong. Hiding alerts is also a risk: a rule that is too broad can hide a real attack.

Decision:

  1. One choke point. Every alert (new_payload, detection, disk usage) is created through store._alert, which asks suppression.Suppressor for a decision. Matching lives in backend/hpintel/suppression.py.
  2. Matchers are optional and ANDed; a rule needs at least one (enforced by the API): command_hash (exact, 64 hex), kind (exact, or prefix when it ends with *), src_ip, src_cidr (IPv4 and IPv6), src_asn (from ip_intelligence.asn; an IP that is not enriched yet never matches), require_no_transfer (no captured payload transfer in the session, store.payload_transferred) and expires_at (exclusive; checked with an injectable clock; the API requires a future value on create and when the value changes on update, so an already expired rule can still be edited or disabled). Disabled and expired rules never match.
  3. Actions: - demote with target_severity: the alert is created at that severity; alerts.original_severity and alerts.suppression_rule_id record the change. A demote rule whose target is not lower than the alert severity is skipped (a rule never raises a severity). - suppress: no alerts row is created. One row goes to suppressed_alerts (unique dedup_key), so repeated detection runs of the same session count once. Nothing is published to /ws or sent by the webhook notifier, because the notifier only reads alerts.
  4. Order: among all matching rules a suppress rule beats a demote rule; inside one action the lowest rule id wins. A rule's hit_count and last_hit_at change once per new alert or suppressed row (dedup repeats do not count).
  5. Hash timing, both directions. sessions.command_hash is only filled for closed sessions by analytics_jobs.fill_command_hashes. A command_hash matcher is never evaluated against the commands of an open session: an attacker may send a known probe sequence first and continue, so a matching prefix must not hide or demote the alert (the alert is raised normally). At raise time a command_hash rule can only match a session that is already closed and whose stored hash is current (command_hash_count = command_count); a missing or stale hash never matches. Such a closed session can be suppressed or demoted at raise time. For alerts raised before the hash existed, a bounded, idempotent housekeeping pass (suppression.reevaluate: alerts of the last 7 days, newest first in pages of 500 alerts, at most 10 pages per run, only alerts with no original_severity and no suppression_rule_id, only closed sessions with a current stored hash) applies demote rules with a command_hash. It never applies suppress rules, so a re-evaluated alert is lowered, never hidden. Consequence: alerts are normally raised while the session is still open, before the hash is stored, so a suppress rule whose only distinguishing matcher is command_hash rarely or never fires. Use demote for command-hash rules (the seed rule does). Dedup keys: a suppressed or demoted first alert occupies its dedup key. For command-level-only classification alerts (no payload transfer) the key is class-ip:<category>:<src_ip>:<UTC day>, so later such sessions of the same IP, category and day are not raised again, neither as an alert nor as a suppressed_alerts row. A session with a captured transfer uses its own per-session key class:<session>:<category> and is decided on its own. Critical alerts are never suppressed: decide skips suppress rules for them, so they fall to a matching demote rule or are raised as they are (for example a critical disk_usage alert; a high one can be suppressed). The API also rejects a suppress rule whose only matcher is require_no_transfer (a suppress rule needs command_hash, kind, src_ip, src_cidr or src_asn).
  6. Alerts are never deleted by this feature (owner decision). Events, sessions, commands, classifications and MITRE techniques are never touched; suppression only affects the alert row.
  7. History. suppressed_alerts has no foreign key to the rule, so deleting a rule (hard delete, admin only) keeps the log; alerts.suppression_rule_id also stays. suppressed_alerts follows the events/alerts retention; rules are never swept. At most 200 rules.
  8. Rules are cached for 30 s in the process and the cache is invalidated on create, update and delete. A generation counter ensures a load that started before an invalidation is not cached. Changes made directly in the database take up to 30 s to apply.
  9. Seed rule (migration 12, idempotent by name known-probe-filter-d882d096): command hash d882d0964774607b8db753f534966863550f4b5a4b10d2b0bc2bfe8ef4bc5404, kind classification:malware_deployment*, require_no_transfer, demote to low. The same hash with a transfer is not demoted.
  10. Rule CRUD is logged at INFO with the actor and rule id only, never the name or note.

Consequences: a mistaken or overly broad rule hides alerts from the dashboard, the WebSocket and the webhook until it is edited or deleted; the Suppressed alerts tab and suppressed_alerts show what was hidden. Operators should prefer demote over suppress and add an expiry to temporary rules (OPERATIONS.md).

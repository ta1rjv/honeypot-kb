Purpose #

This site publishes what the Honeypot Intelligence project has learned: how a contained SSH honeypot is built, what attackers did against it, and which engineering decisions were made. It is written for defenders, researchers and operators of similar systems. It is defensive research; it contains no instructions for attacking or fingerprinting the honeypot.

Data policy #

  • Keep all logs for research. All captured data (events, sessions, payloads, raw logs, TTY recordings) is retained effectively forever on the production host, so older sessions are never lost to automatic pruning (ADR 0010). Disk usage alerts stay active and capacity is an operator responsibility.
  • Snapshot-driven numbers. Every count, table and chart in the statistics pages is generated from a production snapshot (date shown on those pages). No count is typed by hand.
  • Attacker data is attacker-supplied. Usernames, passwords, commands and client strings come from hostile sources. They are shown as data, never as trusted content.
  • Containment first. Captured files are only read, never executed or published.

Sanitization and defanging policy #

  • The production host address, private addresses, management ports, tunnel and host names, virtualization identifiers, operator account names, e-mail addresses, keys, secrets and password hashes are never published. They are described generically (for example "a rented virtual server", "a restricted management access", "a disposable test VM").
  • Attacker indicators (source IPs, credentials, payload hashes, URLs, domains) may appear, from the snapshot tables; any URL or domain quoted in text is defanged.
  • Private key material and captured binaries are never reproduced.
  • A publication gate checks the generated pages for forbidden patterns and fails the build on a match.
  • Details of how to detect this particular honeypot are deliberately summarized only at a high level.

Truth levels #

Statements about the system carry one of these levels, never upgraded without evidence:

Level Meaning
PLANNED Designed or proposed, not built.
IMPLEMENTED Code exists; tested at most by unit tests.
REVIEWED A code review approved it.
VALIDATED Exercised on a real (usually disposable) environment with recorded results.
MEASURED Observed on the production system with recorded output.
UNKNOWN Not established by any source.

Items that were not run are called NOT RUN or NOT VERIFIED, and are not reported as passed.

Licence and warranty #

The source repository is private and no open-source licence has been chosen; all rights are reserved by the repository owner. The site content is provided for information only, without warranty of any kind. Indicators may be wrong, stale or reflect shared infrastructure; verify before blocking anything. The source documents mirrored in the library are the authoritative English text.

Sources #

The curated pages are based on the project documents: README, ARCHITECTURE, THREAT_MODEL, DATA_MODEL, API, the requirements, the decision records, attack patterns, triage reports and research notes. Operational documents of the deployment (runbooks, network and security configuration, release notes, production reports) are not published. Start at the home page.

ADR 0015: Telegram and SMTP notification receivers

Status: accepted (2026-10-15). Supersedes point 6 ("SMTP is deferred") of ADR 0011. Implementation: backend and dashboard IMPLEMENTED on wip/0.5.0, tested against local fakes only (no real Telegram or SMTP server contacted); the firewall part (renderer, setup.sh, wizard, nft golden files, setup.conf keys) is IMPLEMENTED on wip/0.5.0 and tested without a VM; VM validation NOT VERIFIED.

Context: ADR 0011 added one opt-in channel, a signed webhook, and deferred mail. Operators also want a chat message and a mail without running a gateway, and a daily summary of the alerts that stay below the immediate threshold. The containment rules of ADR 0003 and ADR 0011 do not change: every new channel needs its own explicit egress rule for the backend uid hpintel, and nothing an attacker controls may choose the destination.

Decision:

  1. Generalise backend/hpintel/notify.py minimally. A Channel descriptor (name, enabled, minimum severity, rate limit, log target, transport preparation, send function, optional digest) is processed by the existing machinery: candidate selection in severity order, persisted high-water mark per channel (alert_delivery_cursors), one alert_deliveries row per (alert, channel), 3 attempts with 1 minute and 5 minutes backoff, rate limit, batch limit, 15 minute backlog grace. Channel names are webhook, telegram, email (String(16), no schema change). Webhook behaviour is unchanged and its tests run unchanged. Suppressed alerts are never delivered on any channel (they are not alerts rows, ADR 0013); a demoted alert is judged by its demoted severity.
  2. Telegram: POST https://api.telegram.org/bot<TOKEN>/sendMessage with JSON {chat_id, text}; parse_mode is never set. The text is built from the same fields as the webhook, each clipped to 512 characters, as printable ASCII, at most 4000 characters (Telegram allows 4096). HTTP 200 with "ok": false is a failure; HTTP 429 pauses the whole channel for retry_after seconds (bounded to 1 h; the pause is in memory, a restart simply meets the 429 again). The token is part of the URL path: it is never logged, stored, returned or put in an error row; only https://api.telegram.org:443 is logged and returned. Same hardened opener as the webhook (TLS verification on, no redirects, no proxies, per-operation and overall deadlines). Optional HPINTEL_TELEGRAM_CONNECT_IP connects to one literal IP while the TLS server name and certificate verification stay api.telegram.org, so the firewall rule can name one address.
  3. SMTP: stdlib smtplib subclasses on the same deadline sockets (5 s per operation, 20 s per delivery). Modes starttls (587, default) and tls (465); plaintext is refused by configuration and at run time (a server that does not offer STARTTLS fails the attempt before AUTH or MAIL). Certificate and host name are always verified (optional CA file replaces the trust store). Login only when user and password are set, and only after TLS. Messages are email.message.EmailMessage with an ASCII body; the subject holds only controlled fields (severity from the fixed scale, the kind if it matches a fixed character pattern else other, a validated source IP), CR and LF are stripped from every header value, and at most 5 plain recipient addresses are accepted. Error reasons come from exception types and SMTP reply codes, never from server text. If the server refuses some but not all recipients, the delivery still counts as successful (a retry would send duplicates to the accepted recipients); a WARNING SMTP server refused N of M recipients logs the count only, never the addresses. If every recipient is refused the attempt fails as before.
  4. Per channel *_MIN_SEVERITY (default high) and *_MAX_PER_MIN (Telegram 20, e-mail 6).
  5. Digest per channel (Telegram, e-mail; none for the webhook) every *_DIGEST_HOURS (default 24, 0 = off): the alerts below the channel threshold by severity and kind, the top 5 source IPs, and the number of suppressed alerts of the interval; nothing is sent when the interval is empty. It contains only counts, severities, validated kinds and validated IPs. State is the new table notification_digests (migration 13: channel, last_alert_id, last_suppressed_id, last_sent_at), so a restart never repeats a digest; the first pass of a channel only records the current ids. A failed digest is retried 3 times 5 minutes apart and then skipped for that interval.
  6. Configuration (hpintel.env, validated at start and by check-config, errors never echo a value): HPINTEL_TELEGRAM_BOT_TOKEN and _CHAT_ID are an all-or-nothing group; the SMTP _HOST, _FROM, _TO are one group and _USER, _PASSWORD another; bounded lengths and numbers. Secrets live only in hpintel.env.
  7. GET /api/system/notifications keeps its webhook keys and adds channels.telegram and channels.email (enabled, target host only, minimum severity, last success, last error sanitised, sent and failed in 24 h). The Health page shows each channel.

Consequences:

  • Firewall part (IMPLEMENTED, not VM-validated): HP_TELEGRAM_DEST4/HP_TELEGRAM_PORT and HP_SMTP_DEST4/HP_SMTP_PORT (both or neither per pair, one IPv4 address and port, same constraints as the webhook rule) each render one rule for uid hpintel after the uid cowrie drop (order: webhook, Telegram, SMTP, backup); without them a contained host cannot deliver and deliveries fail with timeout. setup.sh needs the hpintel user, warns when hpintel.env disagrees with the keys, and the wizard never asks for the token or the SMTP password.
  • Telegram needs an IP the operator pins (HPINTEL_TELEGRAM_CONNECT_IP) or a DNS answer that matches the firewall rule; api.telegram.org addresses can change.
  • A compromised backend can send the same alert data to the configured chat and relay (accepted residual risk, as for the webhook); the bot token and SMTP password are readable by the hpintel user through hpintel.env.
  • Alert text from attackers reaches a chat and a mailbox. Plain text only (no parse_mode), no attacker text in mail subjects or headers, but clients may linkify URLs in the body.
  • The 429 pause and the digest retry counters are in memory.

Alternatives considered: a mail library or Telegram client library (more attack surface than the standard library); parse_mode MarkdownV2 or HTML (escaping errors would let alert text alter messages); plaintext SMTP or opportunistic STARTTLS (downgradable); a digest computed from timestamps instead of id cursors (restart repeats or gaps); one shared rate limit for all channels (one failing receiver would starve the others).

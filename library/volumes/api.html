Authentication #

POST /api/auth/login   {"username": "admin", "password": "..."}
-> 200 {"token": "[redacted]", "expires_in": 43200, "username": "admin", "role": "admin"}
-> 401 invalid credentials
-> 429 too many failed logins (see limits below)

Roles (0.4.0) #

Role Account May use
admin HPINTEL_ADMIN_USER / HPINTEL_ADMIN_PASSWORD_HASH every route
viewer optional HPINTEL_VIEWER_USER / HPINTEL_VIEWER_PASSWORD_HASH (both or neither) every GET route and the WebSocket, including captured passwords and session replay
  • Write routes are admin-only and answer a valid viewer token with 403 {"detail": "admin role required"}: POST /api/alerts/{id}/ack, POST /api/alerts/ack, POST /api/alerts/{id}/unack, POST /api/alerts/unack, POST /api/alerts/{id}/notes and POST, PUT, DELETE on /api/suppression-rules. Every non-GET route except login is admin-only (enforced by a route-enumeration test).
  • Tokens carry a role claim (admin or viewer) in addition to sub. The role is checked against the current configuration on every request: a token without a role claim (issued before 0.4.0) is accepted only when sub is the admin user; role: admin needs sub = admin user; role: viewer needs a configured viewer with sub = viewer user. Any other token gets 401, so a token stops working once its account is renamed or the viewer is removed (after the hpintel restart).
  • Login verifies exactly one password hash for every request (the admin hash for an unknown username), so the response time does not reveal whether a username exists. Admin and viewer share the limiter rules below (keys are the casefolded usernames, which must differ).

Login rate limits (in memory, per backend process, 15-minute sliding window):

  • Per username: at most 10 failed logins per username. The key is the submitted username stripped of surrounding whitespace and casefolded (" Admin " and "admin" share one bucket). The client IP is not used: behind the SSH tunnel every client is 127.0.0.1.
  • Global: at most 30 failed logins in total across all usernames; once reached, every login (any username, even with the correct password) gets 429 until older failures leave the window.
  • Each attempt is checked and reserved atomically before the password is verified, so concurrent requests cannot exceed either cap. A blocked attempt reserves nothing.
  • A successful login clears that username's bucket and releases the global slot reserved by that attempt; earlier failures still count toward the global cap until they expire.
  • At most 10000 distinct usernames are tracked; the oldest are evicted.
  • The 401 and 429 response bodies are unchanged: {"detail": "invalid credentials"} and {"detail": "too many failed logins, try again later"}.

Send Authorization: Bearer [redacted] on every /api/* call except login and /api/health, and on /metrics. Tokens are HS256 JWTs with exp (default lifetime 12 h, HPINTEL_JWT_TTL_MINUTES). Missing, invalid or expired tokens give 401.

Alert suppression rules (0.5.0, ADR 0013) #

Method Path Notes
GET /api/suppression-rules any role; {items, max_rules}
GET /api/suppression-rules/{id} any role; {rule, hit_count, suppressed_total, recent_suppressed} (latest 50); 404 if unknown
POST /api/suppression-rules admin only; 201 with the rule; 409 for a duplicate name or more than 200 rules
PUT /api/suppression-rules/{id} admin only; replaces the editable fields; 404 if unknown, 409 duplicate name
DELETE /api/suppression-rules/{id} admin only; hard delete (suppressed_alerts keep the history); 404 if unknown
GET /api/alerts/suppressed any role; limit (1-500, default 100), offset; newest first; {items, total, limit, offset}

Body of POST and PUT: name (1-128 printable characters, unique), enabled (default true), action (demote or suppress), target_severity (required for demote, one of critical|high|medium|low|info, not allowed for suppress), optional matchers command_hash (64 hex), kind (exact, or a prefix when it ends with *, <= 64 characters), src_ip, src_cidr (host bits allowed, stored normalised), src_asn (1-2147483647), require_no_transfer, plus expires_at (ISO-8601 UTC; must be in the future on create and when it changes on update, so an expired rule can still be edited or disabled with its expiry unchanged) and note (<= 500 printable characters). At least one matcher is required; a suppress rule needs one of command_hash, kind, src_ip, src_cidr, src_asn (require_no_transfer alone is only allowed for demote). Critical alerts are never suppressed (only demoted). Invalid input gives 422. Rule CRUD is logged with the actor and rule id only. GET /api/alerts/search and GET /api/alerts items carry original_severity and suppression_rule_id (null unless a demote rule lowered the severity).

Acknowledgement audit trail (0.5.0) #

Every real change of an alert's acknowledged state (ack or unack, single or bulk) appends one row to alert_ack_events in the same transaction; repeating an ack or unack that changes nothing writes nothing. actor is the JWT username of the admin (truncated to 128 characters). The optional reason is stripped and must be 0-500 printable characters (an empty value means no reason; control characters, newlines and tabs, or more than 500 characters give 422). The reason is stored only and never logged. Interior newlines and tabs are rejected (422); leading and trailing whitespace is stripped. Acknowledgements made before migration 11 have no event ("no audit record").

Analytics and intelligence endpoints #

Implemented in api_stats.py, api_intel.py, api_alerts.py, api_system.py, api_payload_intel.py and api_reports.py. All need the Bearer token; all GET routes are open to the viewer role.

Time window (since, until) #

Endpoints marked window take an optional half-open window [since, until): - Format: 2026-10-06T00:00:00Z, or the same with a +HH:MM offset; a timestamp without Z or an offset is rejected with 422. Each value is at most 64 characters and the year must be 1970-9998. - Defaults: until = now, since = until - 24 h. The span is at most 366 days. - Buckets: minute buckets up to 3 h, hour buckets up to 48 h, day buckets beyond that (UTC). - The response echoes window (since, until, bucket, previous_since).

IoC export (/api/intel/iocs) #

  • Only observed indicators are exported: source IPs of sessions started in the window, sha256 values of payloads seen in the window, and download URLs from those payload events (http, https, ftp, ftps, tftp; printable ASCII, at most 2048 characters). IoCs extracted from payload contents are not exported. A URL whose authority contains a backslash is dropped (url_rejected).
  • Non-global IP addresses (private, loopback, link-local, documentation, ...; IPv4-mapped IPv6 is unwrapped first) and the networks in HPINTEL_IOC_EXCLUDE are always excluded, both as IPs and as URL hosts. URL hosts are checked after the userinfo is removed and one trailing dot is stripped; legacy numeric forms (127.1, 2130706433, 0x7f000001, 0177.0.0.1) are decoded first, and localhost / *.localhost count as non-global. The JSON format reports the excluded counts and per type a truncated flag (limit reached) and a scan_capped flag (50000 rows read; the result may be partial).
  • Every format is sent as an attachment (hpintel-iocs-<until>.csv, .json or -stix.json) with Cache-Control: no-store.
  • CSV: a cell that starts with =, +, -, @, TAB or CR gets a leading ', so spreadsheet programs do not evaluate it as a formula.
  • STIX 2.1: a bundle of indicator objects. Indicator ids are deterministic (uuid5 of the type and value). created and modified are the global first and last sighting of the indicator and the description holds no window-specific counts, so the same indicator is byte-identical in exports over different windows; only the bundle id depends on the window.

Heuristic indicators (include_heuristic=1, 0.4.0): adds IPv4 addresses, URLs and cryptocurrency wallets (type wallet) extracted from the content of payloads transferred in the window (payloads.extracted_iocs). With the option every item carries evidence (observed or heuristic); a value that is also observed in the window is never exported as heuristic. limit applies per type to observed and heuristic items together, observed first. The same IP filter, URL checks and CSV neutralisation apply; the CSV gets an evidence column; the JSON adds include_heuristic, heuristic (truncated, scan_capped, payloads_scanned) and counts_by_evidence. Heuristic STIX indicators use their own id namespace, confidence 15 and x_hpintel_evidence; wallets have no STIX 2.1 pattern and are exported as JSON / CSV only. Without the option (default 0) the response is byte-identical to the export of 0.3.x (pinned by golden fixture tests).

Payload intelligence notes: extracted_iocs (also returned by /api/payloads) is heuristic, at most 100 values per kind and 8 KiB of JSON per payload. Families rely on the hash of the first 64 KiB, so a truncated copy shorter than 64 KiB is not grouped with its original.

Script clusters (by=script) #

A heuristic grouping of sessions whose command sequences differ only in variable parts. Each of the first 500 commands of a closed session is normalised (normalize_command_v1): whitespace collapsed; URLs (http, https, ftp, ftps, tftp) -> <URL>; dotted IPv4 -> <IP>; hex runs of >= 16 characters -> <HEX>; base64-like runs of >= 24 characters (upper case, lower case and a digit) -> <B64>; remaining digit runs of >= 4 -> <N>. sessions.command_norm_hash is the sha256 of "v1\n" plus the normalised commands joined by newlines, filled by the same background job as the exact command hash. The dashboard labels these groups "heuristic cluster".

Weekly report (/api/reports/weekly) #

JSON: version, hpintel_version, generated_at, period (since, until, week), previous_period, kpis and previous (sessions, unique_ips, logins_ok, logins_failed, commands, new_payloads, alerts_by_severity), top (ASN, country, username, password, client version, HASSH, command; 10 each), new (counts per kind), campaigns (top 10 of the exact kinds command, hassh, payload; script clusters are not reported), iocs (observed_new per type, truncated), health (availability_pct) and containment (cowrie_egress_pkts); the last two are null while host status is disabled or no sample covers the period. format=markdown returns the same report as a deterministic Markdown attachment (hpintel-weekly-<week>.md or hpintel-report-<since>-<until>.md); attacker-controlled strings are stripped of control characters, clipped to 200 characters, HTML-escaped, pipe-escaped and wrapped in a code span. Built reports are cached per period (5 min for an open period, 1 h for a closed one; the same document for admin and viewer).

WebSocket /ws #

  1. Connect to ws://<host>:8000/ws (no token in the URL).
  2. Send as the first message within 5 s: {"type": "auth", "token": "[redacted]"}.
  3. Server replies {"type": "hello", "user": "<username>"}, otherwise closes with code 4401. Admin and viewer tokens are accepted (the feed is read-only); a token whose account no longer matches the configuration is refused like an invalid one.
  4. Server pushes: - {"type": "event", "data": {event_id, timestamp, session_id, source, event_type, severity, src_ip, summary, data}} - {"type": "session", "data": <session row>} - {"type": "alert", "data": <alert row>} - {"type": "tty", "data": {"session_id", "frames": [{"t", "dir": "out|in", "data": <base64>, "ts"}]}} (merged frames, at most 256 KiB per message) - {"type": "ping"} every 25 s
  5. The server closes with 4401 when the token expires; slow clients (send blocked > 10 s) are disconnected.

Response headers #

Every HTTP response carries Content-Security-Policy (default-src 'self', frame-ancestors 'none', ...), X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy: no-referrer; /api/* responses also carry Cache-Control: no-store. No CORS headers are sent (same-origin only).

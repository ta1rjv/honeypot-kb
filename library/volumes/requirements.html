Functional Requirements #

REQ-001 SSH Honeypot Service #

Description: The system shall provide an internet-facing SSH service on port 22 (configurable) that accepts connections from any source IP for the purpose of observing attacker behavior.
State: VALIDATED (2026-10-07: Cowrie on tcp/22, logins recorded in the attack simulation and after a reboot)
Notes: Must not allow real authentication to any actual account; all login attempts shall be recorded regardless of credentials.

REQ-002 Shell Session Recording #

Description: For each SSH session, the system shall record: source IP, source port, destination port, timestamp, username attempted, authentication result, session ID, commands executed, command timing, command arguments, TTY activity, environment information, shell type, exit codes, filesystem operations, downloaded files, created files, deleted files, executed binaries.
State: VALIDATED for commands, auth, TTY, file transfers, emulated processes/files; tamper-evident hashing of recordings NOT IMPLEMENTED
Notes: Recording shall be tamper-evident and stored with cryptographic integrity where feasible.

REQ-003 Live Terminal Viewer #

Description: A web-based dashboard shall display selected attacker sessions in real time, resembling a terminal with monospace font, showing command input and output as they occur.
State: VALIDATED (WebSocket tty frames with an attacker-typed marker, 2026-10-07)
Notes: Shall not depend on polling; shall use WebSocket or Server-Sent Events for low-latency updates.

REQ-004 Event Stream & Storage #

Description: The system shall emit a canonical event model (JSON) for every observable action (SSH_LOGIN, COMMAND, FILE_CREATE, PROCESS_EXEC, NETWORK_CONNECT, etc.) to a durable append-only log.
State: VALIDATED (normalized events in SQLite with session correlation and UTC timestamps; not an append-only log file)
Notes: Events shall include correlation IDs (session_id) and UTC timestamps.

REQ-005 Payload Capture & Analysis #

Description: When an attacker attempts to download or upload a file via wget, curl, scp, sftp, echo, base64, or similar mechanisms, the system shall capture the file, compute its SHA256, record metadata (filename, size, source IP, session ID, download URL), and store it without executing it on the honeypot host.
State: VALIDATED for SCP/SFTP uploads (sha256, type, strings); wget/curl downloads blocked by containment by design; entropy NOT IMPLEMENTED
Notes: Captured payloads shall be stored in a quarantined directory; optional analysis may occur in a separate sandbox/container.

REQ-006 IP Intelligence & Geolocation #

Description: For each unique source IP, the system shall maintain: IP, country, ASN, ISP/organization, reverse DNS, first seen, last seen, number of sessions, authentication attempts, successful sessions, commands executed, payloads, threat score, observed techniques.
State: IMPLEMENTED (Team Cymru DNS, rDNS, optional MaxMind db); not validated with a public IP (only LAN traffic so far); no geolocation without a user-provided mmdb
Notes: Shall use offline databases (e.g., MaxMind DB) or optional API integrations (no hard-coded API keys).

REQ-007 Attack Classification Engine #

Description: The system shall automatically classify observed behaviors into categories: Reconnaissance, Port Scanning, SSH Brute Force, Credential Stuffing, Privilege Escalation, Persistence, Defense Evasion, Command Execution, Malware Download, Malware Execution, Cryptominer Deployment, Botnet Recruitment, Ransomware-like Activity, Web Exploitation, Lateral Movement Attempt, Data Exfiltration Attempt, Proxy/VPN Installation, IRC/C2 Behavior, DNS-related Activity, Suspicious File Activity.
State: VALIDATED (classifications with confidence, evidence and MITRE mapping in the attack simulation)
Notes: Classification shall be based on observed evidence only; confidence levels (High/Medium/Low) shall accompany each classification.

REQ-008 Network Containment #

Description: Outbound network traffic from the honeypot shall be restricted by default-deny firewall rules. Only explicitly permitted outbound traffic (e.g., DNS to trusted resolvers, NTP, API calls to threat intelligence feeds if opt-in) shall be allowed.
State: VALIDATED (uid cowrie egress, loopback and DNS blocked; forwarding refused; ip_forward 0; after reboot)
Notes: Must prevent the honeypot from being used for: internet scanning, SSH brute force, DDoS, spam, malware propagation, credential attacks, proxying, C2 forwarding.

REQ-009 Real-Time Dashboard #

Description: A web dashboard shall provide:
- Live attack metrics (events/min, unique source IPs, authentication attempts, successful logins, payloads captured, high-risk sessions)
- World map of attacker origins (by country/ASN)
- Live sessions table with threat levels
- Terminal view for selected sessions
- Event stream (real-time)
- IP intelligence details
- Attack timeline view
- Payload repository with hash listings
- Analytics over time (attacks/hour, unique IPs/day, top ASNs, top usernames, etc.)
State: IMPLEMENTED (all views built and served, data verified through the API and WebSocket; no automated browser test)
Notes: Dashboard shall not expose unnecessary gradients or generic SaaS styling; it shall favor a dark, technical, dense information architecture.

REQ-010 API Endpoints #

Description: The system shall expose a REST API for:
- GET /api/sessions
- GET /api/sessions/:id
- GET /api/events
- GET /api/events/live
- GET /api/ip/:address
- GET /api/payloads
- GET /api/analytics
- GET /api/threats
Additionally, a WebSocket endpoint for live event streaming.
State: VALIDATED (REST and WebSocket endpoints exercised; auth 401/4401)
Notes: API shall require authentication (token-based) and shall not be exposed to the public internet without proper controls.

REQ-011 Persistence & Recovery #

Description: The honeypot shall survive reboots via systemd services; shall perform health checks on startup; shall rotate logs; shall back up configuration and database; shall restore firewall rules.
State: VALIDATED (reboot test 2026-10-07: services, firewall and data restored; collector resumed) Site note: a reboot of the production host was VALIDATED on 2026-10-10 (18:38 UTC) with release 0.2.x/0.3.0; a production reboot with release 0.3.1 and later is NOT RUN; scenario-based reboots were VALIDATED on disposable VMs.
Notes: On boot, services shall start automatically; failure to start critical services shall trigger alerts.

REQ-012 Observability of the Honeypot Itself #

Description: The dashboard shall expose metrics about the honeypot platform: CPU, RAM, disk usage, network RX/TX, database size, events/sec, active sessions, dropped events, collector health.
State: VALIDATED (/api/health components incl. port-owner check, /metrics)
Notes: Collector/pipeline failures shall be visible on the dashboard.

Non-Functional Requirements #

REQ-013 Security of the Platform Itself #

Description: The dashboard and API shall be protected against: authentication bypass, path traversal, command injection, SQL injection, XSS, CSRF, WebSocket privilege escalation.
State: REVIEWED (security review cycles; hardening in SECURITY.md)
Notes: No default credentials; strong password/API token required for administration.

REQ-014 Data Retention & Disk Usage Control #

Description: The system shall enforce retention policies for: raw events, sessions, payload metadata, payload binaries, analytics. Log rotation shall be enabled; disk usage monitoring shall trigger alerts when thresholds are approached.
State: IMPLEMENTED (database retention and Cowrie file retention timer; unit tested, no prune observed on the VM yet)
Notes: Older data may be archived or deleted according to policy.

REQ-015 Time Synchronization & Log Integrity #

Description: All timestamps shall be stored in UTC; the system shall use NTP for clock synchronization; logs shall be append-only where feasible; cryptographic hashing/chaining of log entries may be used for integrity verification.
State: PARTIAL: UTC everywhere, clock synchronized via the container host (timedatectl: synchronized yes, NTP service in the container inactive); log hash chaining NOT IMPLEMENTED
Notes: NTP source shall be reliable and optionally authenticated.

Acceptance Criteria (Examples) #

Each requirement will have specific, measurable acceptance criteria defined during the PLANNING phase. Examples: - REQ-001: Successfully accept an SSH connection and record login attempt without crashing. - REQ-002: Record a full sequence of commands (whoami -> uname -a -> wget ...) with timestamps and output. - REQ-006: Show correct country and ASN for a known test IP address. - REQ-008: Verify that an outbound connection to an external IP is blocked by firewall. - REQ-010: Retrieve a list of sessions via API with valid authentication token.

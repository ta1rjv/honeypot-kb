Intelligence Pipeline

Raw Cowrie events are turned into intelligence in four steps: normalize, derive, classify, enrich. Every derived fact says where it came from.

1. Normalize and derive

The collector and normalizer give every event a stable taxonomy and a deterministic id. The command parser then derives emulated processes, file operations and network intents from the typed command line. Derived rows carry evidence="derived"; rows read directly from Cowrie carry observed. Network intents from wget or curl have status attempted and never mean a real connection was made.

2. Evidence and confidence model

ADR 0008 (accepted 2026-10-06, IMPLEMENTED):

Confidence Meaning
Suspected A weak or single indicator.
Likely Several consistent indicators, or a strong one without confirmation.
Observed The behaviour itself was seen in the recorded session.
Confirmed Requires a captured payload that is then executed in the same session.

The vocabulary is ordered Suspected < Likely < Observed < Confirmed (definitions in DATA_MODEL.md). Techniques record the confidence of the observation, categories the confidence of the intent. Alerts for severe categories require at least Likely, and every classification lists its evidence strings and event ids, so an analyst can always trace a verdict back to raw events.

3. MITRE ATT&CK mapping

Detection rules and the command parser map behaviour to techniques, for example T1082 system information discovery, T1105 ingress tool transfer, T1059.004 Unix shell, T1222.002 file permission modification, T1098.004 SSH authorized keys, T1070 indicator removal and T1496 resource hijacking. Because bots use one attempt per connection, per-source credential techniques (T1110.001 guessing, T1110.003 spraying) are aggregated by a housekeeping job rather than per session. The thresholds are documented assumptions in the assumptions record. Technique rows can be re-derived for stored sessions after a rule change (redetect-techniques); this was done once on production on 2026-10-16 and left the alert count unchanged (MEASURED). The live technique table is on the Indicators page.

4. IP intelligence (in production)

ADR 0007 (accepted 2026-10-06, IMPLEMENTED):

  • Team Cymru IP-to-ASN data over DNS: ASN, prefix, country, registry, AS name. No API key.
  • Reverse DNS, switchable, because PTR queries reach name servers controlled by attackers.
  • An optional local MaxMind-format database for city and coordinates, supplied by the operator.
  • Results are labelled "external intelligence" and are never treated as identity.

5. Payload analysis

Uploaded files are hashed (SHA256), typed by magic bytes, measured (size, entropy) and scanned for printable strings with URLs, IPs and shell keywords ranked first. ELF headers are parsed. Files that share a head hash are verified byte by byte to find truncated copies of one binary. Files are only read: never executed, never served by the API, never committed to source control.

6. Alert workflow

Alerts have severities, can be searched, acknowledged in bulk and annotated; known noise can be demoted or hidden with suppression rules. Opt-in webhook, Telegram and e-mail channels deliver alerts above a per-channel threshold with rate limits and an optional digest (ADR 0011, ADR 0015). On the production host these channels are not configured (status 2026-10-16).

7. Planned: external reputation enrichment (ADR 0018)

Status: not released. ADR 0018 was accepted on 2026-10-16 for the 0.6.0 work. Its egress and configuration foundation and a pilot client for Shodan InternetDB are IMPLEMENTED on a work branch and unit-tested against local fakes only; review and validation on a VM or against a real provider are NOT VERIFIED. Clients for AbuseIPDB, GreyNoise, URLhaus and VirusTotal are PLANNED.

Design summary:

  • A fixed set of five providers; host names are constants in code, so an operator cannot redirect a provider.
  • Every provider needs its own explicit firewall rule for the backend user only (one to four pinned IPv4 addresses, one port). Without the keys the ruleset does not change.
  • Connections go to pinned addresses with certificate verification against the real host name; no redirects, no proxies, a 64 KiB response cap, per-provider daily and per-minute quotas, persisted pauses on rate limits.
  • An operator command compares the pins with current DNS answers; nothing refreshes the firewall automatically.
  • Results are informational only: they never change a risk score, create or suppress an alert, or enter the IoC export. The pilot never yields a "malicious" verdict because exposure data is not an attacker verdict.
  • Sending an attacker address to a third party discloses research interest, so it is opt-in per provider and the operator must check provider terms.

Provider facts, limits and a DNS snapshot are in the research note (enrichment providers, 2026-10-16); multi-day address stability of the providers is UNVERIFIED.

8. Planned: out-of-band retrieval and sandbox (ADR 0014)

Fetching attacker URLs and detonating samples is PROPOSED only, and deferred (2026-10-15). The design keeps the sensor unchanged and moves retrieval and analysis to separate hosts with one-way, pull-only data flow (ADR 0014).
